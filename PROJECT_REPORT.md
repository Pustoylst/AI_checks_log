# Отчёт о проекте Directum Log Analyzer

## 1. Назначение проекта

Проект предназначен для автоматического анализа ошибок в JSON-логах системы Directum. Пользователь передаёт лог, после чего агент на базе GigaChat:

1. изучает содержимое лога;
2. определяет вероятные причины ошибки;
3. при наличии ссылки на файл или символ обращается к исходному коду;
4. использует найденный код как доказательство;
5. формирует ответ с причинами, доказательствами, ссылками на код и дальнейшими шагами.

Итоговый ответ принудительно формируется на русском языке.

## 2. Цель MVP

Проверить сценарий: «загрузить JSON-лог, запустить анализ и получить объяснение ошибки за один запрос».

Критерии MVP:

- GigaChat вызывается из Python;
- основная модель — `GigaChat-2-Max`;
- при сбое используется `GigaChat-2`;
- агент умеет вызывать `read_git_file` или `search_code_in_repo`;
- результаты инструментов используются в итоговом ответе;
- отсутствие `trace_id` и `repo_paths` не приводит к падению;
- секреты хранятся только в переменных окружения;
- интерфейс должен запускаться вместе с FastAPI без отдельной сборки.

### Этап 5. CI watcher и Git-интеграция

- добавлена конфигурация GitHub через переменные окружения;
- добавлен локальный Git status без необходимости GitHub token;
- добавлено чтение GitHub Checks API;
- добавлен polling watcher failed GitHub Actions runs;
- watcher скачивает логи workflow и передаёт их агенту;
- обработанные `run_id` сохраняются в state-файле и не анализируются повторно;
- `run_id` с уже созданным предложением сохраняются отдельно и не показываются повторно;
- создание Pull Request требует явного `approved=true`;
- локальный режим анализа сохраняется и не зависит от GitHub.

Watcher не изменяет код сам: он только анализирует новые failed runs и выводит результат. Предложение исправления, commit и merge остаются отдельными подтверждаемыми действиями.

### Этап 6. Единый браузерный workflow

- добавлена кнопка проверки локального Git;
- добавлена кнопка запуска CI scan;
- у каждого failed workflow появилась кнопка предложения исправления;
- анализ CI напрямую передаётся в proposal workflow без ручного создания JSON-файла;
- после применения исправления в интерфейсе доступно создание Pull Request;
- добавлен macOS launcher `start.command`, открывающий приложение двойным кликом;
- консоль больше не нужна для рабочих действий после запуска приложения.

### Этап 7. Pull Request workflow

- пользователь может запустить анализ failed CI из браузера;
- после проверки предложения доступна кнопка создания Pull Request;
- сервис создаёт отдельную ветку `agent/fix-...` через изолированную Git worktree;
- исправление применяется только в этой ветке;
- создаётся commit и выполняется push ветки;
- GitHub Pull Request получает заголовок и комментарий с причиной, файлом и diff;
- локальная ветка пользователя и её незакоммиченные изменения не переключаются и не добавляются в PR;
- создание PR требует явного подтверждения.

## 4. Архитектура решения

Сервис состоит из пяти основных слоёв:

1. конфигурация читает credentials и параметры моделей из `.env`;
2. API принимает файл и проверяет JSON;
3. схема данных проверяет непустой JSON-объект;
4. агент отправляет лог GigaChat и обрабатывает вызовы инструментов;
5. инструменты читают и ищут код только внутри указанного репозитория;
6. отдельный слой применения изменений работает только после подтверждения;
7. CI watcher получает failed runs, но не выполняет Git write-операции автоматически.

```text
UploadFile -> LogPayload -> analyze_log -> GigaChat
                                      \\-> repository tools
                                             |
                                             v
                                      итог на русском
```

MCP-сервер не используется: инструменты вызываются напрямую из Python, что соответствует требованиям MVP.

## 7. Ограничения текущей версии

- анализ зависит от доступности GigaChat и корректности credentials;
- ссылки на код пока представлены текстовыми путями и строками;
- нет постоянного хранилища истории запросов;
- нет RAG и векторного поиска;
- нет автоматического исправления без подтверждения пользователя;
- набор Directum-логов ещё нужно расширить;
- `GIGACHAT_VERIFY_SSL_CERTS=false` допустим для разработки, но для production TLS-проверку следует включить.
- предложение зависит от того, сможет ли модель вернуть точный существующий фрагмент кода;
- даже после предложения изменение не выполняется автоматически: требуется подтверждение пользователя.
- для GitHub watcher нужны `GITHUB_TOKEN` и `GITHUB_REPOSITORY`;
- автоматическое создание pull request ещё не реализовано.
- для первого запуска всё ещё требуется однократно настроить `.env` и зависимости.
- для создания PR нужны GitHub permissions `Actions: Read`, `Contents: Read and write`, `Pull requests: Read and write`.
